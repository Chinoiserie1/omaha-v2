## Overview

The backtest system answers: **"How would this KOL's portfolio recommendations have performed historically?"**

It takes consecutive `PortfolioSnapshot` records (generated by the thesis cron), fetches real token prices from Birdeye/Yahoo Finance, and computes weighted returns for each period between snapshots. The result is a cumulative performance timeline starting at $1.

Two execution modes:

| Mode | Trigger | Scope |
|------|---------|-------|
| **Auto-compute** | After each thesis cron creates a new snapshot | Latest period only (incremental) |
| **Full backtest** | `GET /api/kols/:kolId/backtest` | All periods (backfills missing ones) |

## Database Models

### PortfolioSnapshot

Created by the thesis cron. Stores the KOL's recommended portfolio at a point in time.

```prisma
model PortfolioSnapshot {
  id              String    @id @default(cuid())
  kolId           String
  thesisSummary   String
  allocations     Json      // Array of { asset, percentage, conviction, reasoning }
  changes         String[]
  sourceTweetIds  String[]
  createdAt       DateTime  @default(now())

  perfFrom  SnapshotPerformance[]  @relation("PerfFrom")
  perfTo    SnapshotPerformance[]  @relation("PerfTo")

  @@index([kolId, createdAt])
}
```

The `allocations` JSON has this shape:

```json
[
  { "asset": "SOL", "percentage": 35, "conviction": "high", "reasoning": "..." },
  { "asset": "BTC", "percentage": 25, "conviction": "medium", "reasoning": "..." },
  { "asset": "USDC", "percentage": 40, "conviction": "low", "reasoning": "..." }
]
```

### TokenPriceDaily

Cached daily USD prices from Birdeye (Solana tokens) or Yahoo Finance (SPX).

```prisma
model TokenPriceDaily {
  id        String   @id @default(cuid())
  symbol    String
  date      DateTime @db.Date
  priceUsd  Float
  source    String   // "birdeye" or "yahoo"

  @@unique([symbol, date])
  @@index([symbol, date])
}
```

### SnapshotPerformance

Computed return for a period between two consecutive snapshots.

```prisma
model SnapshotPerformance {
  id              String   @id @default(cuid())
  kolId           String
  fromSnapshotId  String
  toSnapshotId    String
  periodReturn    Float    // e.g. 0.05 = +5%
  cumulativeValue Float    // running product, starts at 1.0
  periodDays      Int
  details         Json?    // per-asset breakdown
  computedAt      DateTime @default(now())

  @@unique([fromSnapshotId, toSnapshotId])
  @@index([kolId, computedAt])
}
```

The `details` JSON has this shape:

```json
{
  "SOL": { "weight": 0.35, "priceFrom": 120.5, "priceTo": 135.2, "assetReturn": 0.122 },
  "BTC": { "weight": 0.25, "priceFrom": 63000, "priceTo": 64500, "assetReturn": 0.024 }
}
```

## Price Data Pipeline

**Source**: `src/services/price.service.ts`

### ensurePricesForSymbols(symbols, from, to)

Entry point. Called before any period computation to guarantee price data exists.

1. Deduplicates the symbol list
2. Filters out stablecoins (USDC, USDT, DAI, BUSD, PYUSD — hardcoded to $1)
3. For each remaining symbol:
   - **SPX** → calls `fetchAndStoreSP500Prices()` (Yahoo Finance)
   - **Others** → checks `countPricesInRange()` in DB; if 0 cached rows → calls `fetchAndStorePrices()`
4. Sleeps 500ms between Birdeye calls (rate limiting)

### fetchAndStorePrices(symbol, from, to)

Fetches daily OHLCV from Birdeye for a Solana token.

1. Looks up the token's mint address via `findAssetBySymbol()` (from `TradeableAsset` table)
2. Calls `GET /defi/history_price` with `type=1D`, unix timestamps, and `X-API-KEY` header
3. On 429 (rate limit): waits 5s and retries once
4. Stores each day's close price via `priceRepo.upsertDailyPrice()`

### fetchAndStoreSP500Prices(from, to)

Fetches S&P 500 daily prices from Yahoo Finance (`^GSPC` chart endpoint). Stores as symbol `"SPX"` with source `"yahoo"`.

### getPriceOnDate(symbol, date)

Returns the USD price for a symbol on a given date.

1. Stablecoin? → returns `1`
2. Exact date lookup in `TokenPriceDaily` → returns if found
3. Near-date fallback: `findPriceNearDate()` searches ±3 days, returns closest (ordered desc)
4. Not found → returns `null`

## Period Computation (Core Math)

**Source**: `backtest.service.ts` → `computePeriod()` (line 46)

Given two consecutive snapshots (`current` → `next`), computes the weighted portfolio return.

### Algorithm

```
Input: current snapshot, next snapshot, prevCumulativeValue

1. Parse allocations from "current" snapshot (the "from" side)
2. Validate allocation sum (warns if not ≈100%)

3. For each allocation:
   a. weight = percentage / 100
   b. priceFrom = getPriceOnDate(asset, current.createdAt)
   c. priceTo   = getPriceOnDate(asset, next.createdAt)
   d. assetReturn = (priceTo - priceFrom) / priceFrom
      (if either price is missing or priceFrom ≤ 0 → assetReturn = 0)
   e. periodReturn += weight * assetReturn

4. cumulativeValue = prevCumulativeValue * (1 + periodReturn)

Output: PeriodResult {
  fromSnapshotId, toSnapshotId,
  fromDate, toDate,
  periodReturn,       // e.g. 0.032 = +3.2%
  cumulativeValue,    // e.g. 1.032
  periodDays,         // calendar days between snapshots
  details             // per-asset breakdown
}
```

### Example

A snapshot with 60% SOL and 40% BTC, where SOL went from $100→$110 (+10%) and BTC from $60k→$61.2k (+2%):

```
periodReturn = 0.60 * 0.10 + 0.40 * 0.02 = 0.068 (+6.8%)
cumulativeValue = 1.0 * 1.068 = 1.068
```

## Auto-Compute Mode

**Source**: `backtest.service.ts` → `computeLatestPeriod()` (line 111)

Called by `thesis.service.ts` (line 303) after creating a new `PortfolioSnapshot`. Wrapped in a non-fatal `try/catch` so thesis cron never fails because of backtest errors.

### Flow

1. Fetch the 2 most recent snapshots for the KOL (ordered desc)
2. If fewer than 2 → exit (need a pair)
3. Check if this pair already has a `SnapshotPerformance` row → exit if yes (idempotent)
4. Collect asset symbols from the "from" snapshot's allocations
5. Call `ensurePricesForSymbols()` for the date range (with ±1 day buffer)
6. Fetch the latest `SnapshotPerformance` to get `prevCumulativeValue` (defaults to 1 if first period)
7. Call `computePeriod()` to get the result
8. Upsert the `SnapshotPerformance` row

### Integration point

```typescript
// thesis.service.ts, line 301-306
// Compute backtest performance for this new period (non-fatal)
try {
  await computeLatestPeriod(kolId);
} catch (err) {
  logger.warn({ err, kolId }, "Failed to compute period performance (non-fatal)");
}
```

## Full Backtest Mode

**Source**: `backtest.service.ts` → `runBacktest()` (line 164)

Triggered by the API. Computes the complete performance timeline, backfilling any missing periods.

### Flow

1. Fetch up to 500 snapshots for the KOL
2. If fewer than 2 → return empty result (`totalReturn: 0`, `latestCumulativeValue: 1`)
3. Sort snapshots ascending by `createdAt`
4. Collect all unique asset symbols across all snapshots
5. Call `ensurePricesForSymbols()` for the full date range (with ±1 day buffer)
6. Load all stored `SnapshotPerformance` rows into a lookup map (key: `fromId:toId`)
7. Iterate through consecutive pairs:
   - **If stored period exists**: reuse `periodReturn` but **recompute** `cumulativeValue` from the running product (see [staleness fix](#cumulative-value-staleness-fix))
   - **If missing**: call `computePeriod()` and store the result
8. Calculate `totalReturn = cumulativeValue - 1`
9. Return `BacktestResult`

### Return type

```typescript
interface BacktestResult {
  kolId: string;
  snapshotCount: number;
  periods: PeriodResult[];
  totalReturn: number;              // e.g. 0.15 = +15%
  latestCumulativeValue: number;    // e.g. 1.15
}
```

## API Layer

**Route**: `src/routes/backtest/index.ts`
**Handler**: `src/routes/backtest/handlers/run-backtest.ts`

```
GET /api/kols/:kolId/backtest
```

### Handler logic

1. Validates the KOL exists via `kolRepo.findKolById()`
2. If not found → `404 { error: "KOL not found" }`
3. Calls `runBacktest(kol.id)`
4. On error → returns a safe default:
   ```json
   { "kolId": "...", "snapshotCount": 0, "periods": [], "totalReturn": 0, "latestCumulativeValue": 1 }
   ```

This ensures the frontend always gets a valid response shape, even if price APIs are down.

## Snapshot Lifecycle

### Retroactive Backfill (Automatic)

`synthesizeThesis()` automatically detects and backfills gaps between a KOL's earliest tweet activity and their earliest existing snapshot. This works for both new and existing KOLs — no manual deletion needed.

**How it works:**

1. Fetches the earliest existing snapshot and all relevant classified tweets
2. Compares the oldest tweet's `postedAt` date against the earliest snapshot's `createdAt`
3. Two paths:
   - **Cold start** (no snapshots): full retroactive generation from all tweets
   - **Gap backfill** (tweets older than earliest snapshot): generates retroactive snapshots only for tweets before the earliest snapshot, then falls through to the incremental path

**Retroactive generation** (shared by both paths):

1. Sorts tweets by `tweet.postedAt` (not `classifiedAt` which is bulk classification time)
2. Calls `generateWeeklyWindows(earliest, latest)` to create Mon–Sun time windows
3. For each non-empty window, calls `synthesizeSingleSnapshot()` with `createdAt = window.endDate`
4. First window: cold start prompt (all tweets up to that point). Subsequent windows: incremental prompt (previous thesis + new window tweets)
5. Conviction decay uses `window.endDate` as reference date (historical accuracy)

**Example**: Mert was added Feb 23 with a single snapshot. He has tweets since Nov 2025. On next algo run, the gap (Nov 2025 → Feb 23 2026) is detected and ~4 weekly retroactive snapshots are backfilled automatically. The backtest now covers the full tweet history.

### Incremental Updates (Cron)

Once retroactive snapshots exist and no gap remains, subsequent cron runs create one snapshot per cycle with new tweets since the last snapshot. This is the normal steady-state.

### Idempotency

Once backfilled, the gap check (`oldestTweetDate < earliestSnapshot.createdAt`) becomes false because the new retroactive snapshots now cover those dates. The backfill won't re-run on subsequent cron cycles.

## Design Decisions & Edge Cases

### Cumulative Value Staleness Fix

When `runBacktest()` encounters a stored period, it reuses the stored `periodReturn` but **recomputes** `cumulativeValue` from the running product:

```typescript
cumulativeValue = cumulativeValue * (1 + stored.periodReturn);
```

This prevents staleness: if a middle period gets recomputed (changing its `periodReturn`), later periods' cumulative values automatically correct during the next full backtest.

### Near-Date Price Fallback

`findPriceNearDate()` searches ±3 days from the target date. This handles weekends, holidays, and tokens with sparse trading data. The fallback returns the closest price ordered by date descending (most recent first).

### Missing Prices → 0% Return

If a price can't be found for an asset (even with the ±3 day fallback), the asset is treated as having 0% return for that period. A warning is logged. This prevents one missing price from breaking the entire backtest.

### Allocation Sum Validation

If allocations don't sum to ~100% (tolerance of 1%), a warning is logged but computation continues. The math still works — the weighted sum just won't represent a fully-invested portfolio.

### Non-Fatal Integration

The auto-compute call in `thesis.service.ts` is wrapped in `try/catch`. The thesis cron's primary job (creating snapshots) is never affected by backtest failures.

### Idempotent Computation

`computeLatestPeriod()` checks for an existing `SnapshotPerformance` row before computing. Running the thesis cron twice for the same period doesn't create duplicates.

### Rate Limiting

- 500ms sleep between Birdeye API calls (via `ensurePricesForSymbols`)
- On 429 from Birdeye: 5s wait + single retry
- Price data is cached in `TokenPriceDaily` — subsequent requests for the same symbol/range skip the API entirely
